# SRE 問卷 design review 與改進方案

日期：2026-10-07。審查基準：main `47bd1b4` 與 `docs/DESIGN.md`。本文件隨設計 PR 交付；程式可靠性修正另見 code review PR 與 `doc/CODE_REVIEW.md`。

## 1. 判斷與範圍

原設計值得保留的是：雙角色措辭、行為與實證交叉檢視、六維度、按能力前置排序，以及結果僅用作團隊對話。主要問題是「一個分數同時混入能力、資料可見度、事件頻率與工具選型」，因此目前的分數不能視為經過驗證的組織成熟度量表，也不宜直接拿來比較團隊。

本次完成互斥區間、資料不足的可選路徑、評估範圍、風險導向措辭與幾項 UI／文件落差。下文的 v2 提案尚未實作；不把設計提案冒充現有功能。

## 2. 選項不完整／邊界重疊：採用可檢查的作答契約

每題先寫下「量測對象、觀察期間、分母、四個分支與缺資料路徑」，再寫文案。數值型題的每個合法值應剛好落在一個分支；行為型題可採累進描述，但必須明示「全部條件都符合，選最高的一級」。

本次修訂：

| 題目 | 原問題 | 現在的規則／邊界例子 |
|---|---|---|
| q04 決策 | 半年到一年沒有選項；一季與半年重疊 | 從未；超過六個月或記不清時間；六個月內但超過三個月或無法指出決策；三個月內且可指出決策及其數據。六到十二個月落第 2 項 |
| q08 改善完成 | 高於 70% 卻未驗證效果無選項；尚未到期也當未完成 | 已到期完成數／全部已到期數。無改善紀錄；低於 30%；至少 30% 但低於 70% 或效果未驗證；至少 70% 且效果已驗證。80% 未驗證落第 3 項 |
| q11 告警 | 50%、80% 重疊；兩種角色回想期間不同 | 過去 30 天、每次送達值班者的 page（含重複）作分母。比例 [0,25)、[25,50)、[50,80)、[80,100]；50% 落第 3 項 |
| q14 回復 | 15、60 分鐘同時落兩項；回復終點含糊 | 最近六個月一次變更事故，發現到使用者服務恢復。>240、[60,240]、[15,60)、[0,15) 分鐘；15→第 3 項、60→第 2 項、240→第 2 項 |

q08 允許使用最近六個月事故回應演練的改善紀錄，但這是機制證據，不能直接推論真實事故回復能力。q11 沒有 page、q14 沒有變更事故均可選無資料；q08 現在主管與工程師都可以回報無樣本／紀錄不足。

這仍保留 0–4 的既有資料格式與 0→1 保守計分，所以無樣本仍可能拉低分數。結果頁與起始頁已明確揭露這項限制，沒有宣稱它能證明能力不存在。真正解法需要下一節的資料模型。

### 下一版的標準題型

不要只讓翻譯檔自行描述數值區間。建立語言中立的題型資料：

- `percent`：有效範圍 0–100，分母與期間、互斥 bands。
- `duration`：非負分鐘，起點與終點、互斥 bands。
- `behavior`：每級必要行為清單，避免「有工具就算達成」。
- `evidence`：證據來源、樣本數、最近驗證日；只需類型和日期，不蒐集事故內容或客戶資料。

由資料產生選項文案並用參數化測試覆蓋 0、25、30、50、70、80、100%、15、60、240 分鐘與小數邊界；必要時用屬性測試檢查每個合法數值恰有一個分支。q08 同時問完成比例與效果驗證，v2 應拆成兩個輸入，避免混合兩種構念。

## 3. 讓內容貼近實務：先固定範圍，再看行為與證據

### 本次已實作

起始頁提示選定一個團隊及一個具代表性的正式環境服務，全程維持相同範圍；未另訂期間使用過去 90 天。此範圍目前是作答指引，尚未新增服務名稱欄位，避免不必要的識別資料。

q02 用約定檢視週期，取代「一定每季」；q03 認可實際演練政策，避免團隊必須先把錯誤預算用光才有機會達到最高描述。q09 問症狀、服務、變更、依賴訊號能否關聯，traces 僅在有助診斷時使用。q12 看風險適當的檢查、受控發布及驗證過的回復途徑。q18 看符合風險的上線準備與責任驗證，q19 看中斷、疲勞、約定上限與獲得資源的改善。

### v2 建議的 20 題內容藍圖（尚未實作）

每題仍可提供主管／工程師措辭，但量測的構念、範圍、期間必須一致。證據可存在團隊自己的系統，不要求上傳機密文件。

| 題 | 核心問題 | 具體證據／追問 |
|---|---|---|
| q01 | 重要使用者旅程是否有可量測 SLI？ | 成功、延遲／新鮮度／正確性；分子分母、來源、盲點 |
| q02 | SLO 是否有業務共識與明確 owner？ | 目標、窗口、檢視日；避免自動把 99.9% 當標準答案 |
| q03 | 預算政策是否能實際執行？ | 觸發條件、owner、例外、可靠性 backlog；演練亦可 |
| q04 | 數據最近是否改變了決策？ | 一次可說明的取捨及後續結果；不是只看是否開會 |
| q05 | 事故中是否能快速建立協作與溝通？ | 嚴重度、指揮、升級、記錄者、狀態更新；小團隊可兼任 |
| q06 | 檢討是否找出系統性原因？ | 發現／回應時間線、促成因素、可執行行動，避免止於人為疏失 |
| q07 | 學習是否改變其他服務的行為？ | 同類缺陷在其他服務的修正與重複事故趨勢；分享會只是手段 |
| q08 | 到期且高風險的改善是否有效？ | 按期完成率＋效果驗證分開記錄；加 owner、逾期理由，避免小工單灌比例 |
| q09 | 能否從使用者症狀縮小故障範圍？ | 最近事故或演練的診斷時間、訊號關聯；不以工具數量評分 |
| q10 | 叫醒人的告警是否值得立即處理？ | 使用者影响、緊急性、runbook、可行動性；ticket 與 page 分離 |
| q11 | page 的訊號品質如何？ | 有效比例之外，同時看 page／輪值、重複、漏報與樣本數 |
| q12 | 變更風險是否受控且可回復？ | 自動檢查、受控發布、feature flag／roll-forward／rollback；資料變更需獨立考慮 |
| q13 | 變更與事故能否追溯？ | 部署標記、版本、變更失敗率；同一服務與期間內看趨勢 |
| q14 | 真實變更事故如何恢復？ | failed deployment recovery time、樣本數、嚴重度；單次事件不用作通用等級判定 |
| q15 | toil 是否被辨識與量測？ | 抽樣工作時間、重複性、可自動化、隨服務規模增長的部分；不把所有維運視為 toil |
| q16 | 自動化是否安全且有人維護？ | 版本、測試、權限、審計、dry-run、失敗回復、owner；不是腳本越多越好 |
| q17 | toil 消除是否產生持續效果？ | 每週節省工時、錯誤／中斷減少、維護成本；小團隊不強求 sprint 制度 |
| q18 | 服務責任是否清楚且可履行？ | owner、依賴、升級聯絡、支援時段、風險適當的上線檢查 |
| q19 | 值班是否可持續？ | 夜間中斷、可輪值人數、集中度、補休、疲勞、超標行動；與值班者核對 |
| q20 | 可靠性取捨是否透明且有後續？ | 協商紀錄、決策者、政策例外、資源承諾、可靠性工作真的完成 |

另加不計分的情境模組：服務關鍵性、流量／用戶影响、資料敏感度、支援時段、RTO/RPO、主要依賴。依情境提供備份還原演練、容量與負載測試、降級／限流、依賴故障、資料完整性及 DR 建議。這些是目前 20 題明顯未涵蓋的重要可靠性實務，不能因問卷高分就忽略。

## 4. 計分與推薦的設計改進

### 4.1 缺資料不是低能力

v2 將答案改為 `{ level?: 1|2|3|4, evidenceStatus: observed|unknown|no_event|not_applicable, sampleCount?, observedAt? }`，明確區分：

| 狀態 | 解讀 | 建議行動 |
|---|---|---|
| observed | 有可支持行為的樣本 | 計算能力分數，呈現證據新鮮度 |
| unknown | 作答者不知／紀錄不足 | 蒐集資料、確認 owner，提示可見度缺口 |
| no_event | 窗口內沒有事件 | 不假造 0% 或 100%；提議演練，標示證據不足 |
| not_applicable | 依服務風險與性質不適用 | 要求理由類型；不任意排除，不能拿來洗高分 |

顯示「能力分數」與「證據覆蓋率」兩條獨立資訊。有效實證不足時顯示資料不足，避免輸出精確的校正等級。最低有效題數與權重需經試填校準；不要憑直覺宣稱統計信賴區間。需要版本化 DB payload／share 格式與舊版遷移，不能把新 enum 塞進舊版 0–4。

### 4.2 不把通用速度門檻當成熟度

q14 的 <15 分鐘只是原問卷的啟發式分段，不是 SRE 或 DORA 的通用合格線。重大資料修復與可即時回滾的前端變更不可橫向等同。v2 應使用同一服務內的事件樣本、恢復目標與趋勢，並保留分佈／樣本不足說明。

### 4.3 推薦必須可起步、可驗證

目前 N11 以基本 CI/CD（q12≥2）為非節點前置。當只缺 q12 且 q12=1，會只有「暫緩」而沒有「現在做」。v2 應新增基本 CI/CD 節點，或把缺失的非節點前置轉成起步行動，附成功條件，不能讓使用者只看到不可做的高階建議。

保留最多兩件近期行動，但每件應说明觸發答案、前置、範圍、owner、投入估計、兩週可交付成果、驗證方式。例如「盤點 30 天 page，標注是否需立即人工處理，移除三條重複告警；下個輪值比較夜間中斷及漏報」，比「告警有效率提高到某百分比」更可執行。

推薦相依深度的程式錯誤另在 code PR 修正。節點自身條件達成與前置排序為原設計接受的兩個概念，未擅自改成必須所有祖先都達成才算已有能力。

### 4.4 校準方式

先做 5–8 位主管／工程師認知訪談，看是否能找到自己的答案；再用不同規模、服務型態的團隊試填、與實際事件資料對照。檢查角色間理解一致性、缺資料比例、完成時間、改動後的誤判與行動可用性。權重 1／1.5、1.5 分落差與木桶上限目前都是啟發式規則，未提供實證有效性，不適合作為績效考核。

## 7. 參考依據

本文件的門檻、題目與階段安排是審查建議，不是引用來源的標準。

- [Google SRE Workbook：Implementing SLOs](https://sre.google/workbook/implementing-slos/)：以使用者需求、可量測指標及有實際約束力的預算政策支持取捨。
- [Google SRE Workbook：Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)：告警需兼顧可行動性、偵測與噪音，不只追求告警比例。
- [Google SRE Book：Eliminating Toil](https://sre.google/sre-book/eliminating-toil/)：辨識手動、重複、可自動化且沒有持久價值的工作，保留工程改善時間。
- [DORA：Software delivery performance metrics](https://dora.dev/guides/dora-metrics/)：在服务情境下量測交付與恢復表現；不把單次回復分鐘數冒充普遍成熟度基準。
