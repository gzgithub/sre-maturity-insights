## 0. 重點摘要

1. **同一套題庫、兩種問法。** 主管／架構師版與工程師版共用評分基準，只有題幹措辭、結果頁行動建議與「我不確定」選項不同，兩種角色的結果可互相比對。
2. **20 題：14 題情境題加 6 題實證題。** 實證題問「上一次」發生了什麼，用來校正自我美化。每題四段情境，15 秒內可答完。
3. **三道評分防線：** 實證題加權、敘述與實證落差提示、整體等級受最弱維度限制。
4. **建議引擎以「能力節點加前置條件」排序。** 前置條件未達的項目不推薦，並說明為什麼暫緩。最多三條：現在做、下一步、暫緩。
5. **完成後須輸入姓名與 Email 才能看結果（v0.2 新增）。** 為未來收費與後續分析預留，附明確同意聲明。評分仍在瀏覽器端計算，但姓名、Email 與填答會存到後端。
6. **分享網址只含角色與答案，不含任何個資。** 受分享者看到摘要版，完整建議需自己完成問卷。
7. **多語系從第一天就以 i18n 架構建置。** 邏輯與文字完全分離，新增語系只需新增一組語系檔。

## 1. 定位與設計原則

- **測治理與行為。** 問「事故後的改善項目有沒有結案」，不問「有沒有裝某工具」。
- **情境選擇優於有／無。** 每題四段具體情境，使用者選最接近團隊現況的一段。
- **實證優於自述。** 「上一次」類題目要求具體事實，壓縮美化空間。
- **建議要有順序。** 不是補最弱維度，而是依前置條件決定先後。
- **誠實揭露限制。** 自評必有偏誤，結果只是自我檢視的起點，不是稽核。這點固定顯示在頁面上，也是面試中展現成熟度的地方。

## 2. 與初版構想的差異（v0.1 → v0.2）

| 項目 | 初版構想 | v0.2 | 原因 |
|---|---|---|---|
| 個資 | 不登入、不收 Email、無資料保存 | **姓名與 Email 為必填，後端保存** | 未來收費、後續寄送進一步分析與聯絡 |
| 隱私主張 | 「全程瀏覽器端，不涉及資料保存」 | 評分仍在瀏覽器端，**提交時儲存聯絡資料與填答**；需隱私權政策與同意聲明 | 上一項的直接後果。頁面文案不可再宣稱「不保存資料」 |
| 分享網址 | 完整結果 | **摘要版**（等級、雷達圖、各維度等級），不含建議與個資 | 保留完整建議作為未來付費差異點 |
| 選項順序 | 一律隨機打散 | **只打散情境題；實證題維持自然順序** | 實證題選項是遞增的數值區間（如 25%／50%／80%），打散會讓人誤選 |
| 建議節點 | 12 個 | **17 個** | 原設計未覆蓋 Q7、Q9、Q13、Q16、Q19，補足後 20 題都有對應 |
| 語系 | 未規劃 | zh-TW＋en，預留 zh-CN、ja | 見第 10 節 |
| 隱私聲明 | 未規劃 | **本系統有獨立的隱私權政策，與部落格完全分開** | 這是另一個網站，個資的蒐集者、目的與聯絡窗口都要獨立說明，不得沿用或指向部落格的聲明 |

## 3. 填答者與動態內容

### 3.1 角色（必選）

| 項目 | 主管／架構師版（`manager`） | 工程師版（`engineer`） |
|---|---|---|
| 題幹 | 問組織與機制（「團隊如何…」） | 問親身經驗（「你上次…」） |
| 選項 | 四段情境完全相同，以「團隊」為主詞 | 同左 |
| 「我不確定」 | 無 | 部分題目提供（見題庫） |
| 結果頁行動 | 治理動作、跨團隊協調 | 自己能做的小動作＋可帶去跟主管談的一句話 |

**「我不確定」的處理：** 計 1 分，並在結果頁標示「透明度缺口」。工程師不知道團隊有沒有錯誤預算政策，本身就是成熟度訊號：政策若存在卻沒傳到第一線，等於沒有生效。

### 3.2 開場情境題（不計分，只用來調整建議）

- **團隊規模** `team`：`lt5`（少於 5 人）、`5to15`（5 到 15 人）、`gt15`（多於 15 人）
- **服務型態** `svc`：`internal`（內部平台）、`external`（對外 SaaS／產品）、`hybrid`（混合）

**調整規則（v0.2 範圍）：**

- `lt5`：不把 production readiness review（Q18 L4 描述）與全面自助化（Q16 L4 描述）當作「下一級」建議，結果卡片以「小團隊可略過」註記；計分不受影響。
- `svc`：v0.2 只蒐集並存入資料庫，供日後分析。尚未影響文案。

## 4. 等級與計分

**四級：** L1 被動應對、L2 標準化、L3 量化管理、L4 持續優化。選項在畫面上不顯示級別。

### 4.1 題目計分

- 每題 1 到 4 分。所有「不確定／無資料／無事件樣本」選項以 0 記錄、保守計為 1 分，並標記為透明度缺口。這表示證據不足，不足以證明能力不存在。
- 權重：實證題 1.5，情境題 1.0。

### 4.2 維度分數

| 指標 | 計算 |
|---|---|
| **自評線** | 該維度情境題的平均分 |
| **校正線** | 該維度所有題目的加權平均（實證題權重 1.5） |
| **等級** | 以校正線分數判定：`< 1.75` → L1；`< 2.50` → L2；`< 3.25` → L3；其餘 L4 |

### 4.3 整體等級

1. 整體分數 ＝ 六個維度校正線分數的平均。
2. 以第 4.2 節門檻轉成等級。
3. **木桶限制：整體等級不得超過最弱維度等級加一級。** 一個維度崩壞時，其他維度的高分不能代表整體水準。
4. 若限制生效，結果頁須說明「整體等級受 X 維度限制」。

### 4.4 落差提示

同一維度中，**情境題平均減實證題分數 ≥ 1.5**，顯示「你的描述比最近一次實例樂觀，或缺少實證；缺少事件樣本時，請先確認資料再判斷能力」。雷達圖同時畫自評線與校正線。

## 5. 題庫

**維度 ID：** `d1` 可靠性目標與量測、`d2` 事故管理與事後檢討、`d3` 可觀測性與告警品質、`d4` 變更與發布安全、`d5` Toil 與自動化、`d6` 組織與治理。

**作答範圍與規則：** 先選定一個團隊及一個具代表性的正式環境服務；全程保持相同範圍。未另訂期間的題目以過去 90 天為準。描述題選「全部條件有證據支持」的最高描述；不是選最佳的一項工具。無資料／無事件樣本目前以 0 表示並保守計為 1 分，不代表已證明能力不存在；下一版應分開表示（詳見 [設計審查](../doc/DESIGN_REVIEW.md)）。

**題目 ID：** `q01` 到 `q20`。🔎 為實證題（選項是具體事實，不是情境描述）。

**選項 ID：** `1` 到 `4` 對應 L1 到 L4；`0` 為「我不確定」類選項。畫面上不顯示級別。

**i18n key 慣例：**

- `questions.<id>.stem.manager`／`questions.<id>.stem.engineer`
- `questions.<id>.options.1` 到 `.4`
- `questions.<id>.unsure`（若該角色提供）

### 維度 1：可靠性目標與量測

**q01　SLI 定義**
- 主管版：團隊用什麼判定服務「夠可靠」？
- 工程師版：有人問你「現在服務健康嗎？」，你們靠什麼回答？
- L1：沒有明確指標，靠使用者抱怨或感覺
- L2：有基礎監控（CPU、存活檢查），但沒有使用者視角的指標
- L3：核心服務有 SLI（成功率、延遲等）並持續量測
- L4：SLI 從使用者旅程導出，定期校正是否仍貼近使用者感受

**q02　SLO 設定**
- 主管版：可靠性目標的現況？
- 工程師版：你的核心服務有目標數字嗎？有人對照過嗎？
- L1：沒有目標
- L2：文件或口頭有寫「99.9%」，但沒人對照實際量測
- L3：核心服務有實際量測的 SLO 與儀表板，依約定週期檢視
- L4：SLO 與產品／業務共同協商，依數據調整，有人為它負責
- 工程師版提供額外選項：我不確定

**q03　錯誤預算**
- 主管版：錯誤預算在團隊裡扮演什麼角色？
- 工程師版：你看過剩餘錯誤預算的數字嗎？它出現在哪些場合？
- L1：沒用過或沒聽過
- L2：知道概念、算過，但沒人看
- L3：定期計算剩餘預算，並在 review 會議中討論
- L4：預算耗盡有明文政策，包含行動、負責人及例外流程，且實際執行或演練過
- 工程師版提供額外選項：我不確定

**q04　🔎 數據影響決策**
- 主管版：上一次 SLO 或錯誤預算數據改變了一個實際決策，是什麼時候？
- 工程師版：你記得上一次因為 SLO 數字而改變排程或做法，是什麼時候？
- 1：從未因此改變決策
- 2：最近一次在六個月以前，或記不清楚時間
- 3：六個月內有，但已超過三個月，或無法同時說出具體決策與支持數據
- 4：三個月內有，且能說出具體決策與使用的 SLO／錯誤預算數據

### 維度 2：事故管理與事後檢討

**q05　事故回應流程**
- 主管版：重大事故發生時，團隊如何運作？
- 工程師版：上次半夜或假日出事，你到場後的第一個十分鐘發生了什麼？
- L1：誰看到誰處理，沒有分工
- L2：有值班與升級路徑，但事故中的角色臨時決定
- L3：有嚴重度分級、明確角色（事故指揮、對外溝通）與 runbook
- L4：定期演練（game day），流程依演練與事故回饋修訂

**q06　事後檢討**
- 主管版：事故結束後，團隊如何處理？
- 工程師版：事故結束後，你參與的檢討長什麼樣子？
- L1：口頭討論
- L2：重大事故會寫文件，但常止於「人為疏失」
- L3：無究責格式，找出系統性原因並產出改善項目
- L4：改善項目有負責人、期限、追蹤至結案，並回頭驗證有效

**q07　學習擴散**
- 主管版：事故經驗如何在組織內流動？
- 工程師版：別組的事故你會知道嗎？你從中學到東西嗎？
- L1：只有當事人知道
- L2：文件存在，但少有人讀
- L3：定期跨團隊分享、review
- L4：事故資料被統計（重複原因、MTTR 趨勢）並影響 roadmap

**q08　🔎 改善項目完成度**
- 主管版：六個月內最近一次重大事故或事故回應演練，已到期改善項目的完成比例？以「已完成且已到期項目／全部已到期項目」計算；無樣本請選無資料。
- 工程師版：六個月內最近一次重大事故或事故回應演練，已到期改善項目的完成比例？以「已完成且已到期項目／全部已到期項目」計算；無法確認紀錄請選無資料。
- 1：事故／演練需要後續改善，卻未記錄改善項目
- 2：有改善項目；截至今天已到期的項目，完成比例低於 30%
- 3：完成比例至少 30%，但未達 70%，或尚未驗證已完成項目的效果
- 4：截至今天已到期的項目，至少 70% 已完成，且已驗證已完成項目的效果
- 兩版皆提供額外選項：有改善項目但尚無已到期項目／六個月內無事故或演練／無法確認紀錄

### 維度 3：可觀測性與告警品質

**q09　可觀測性覆蓋**
- 主管版：團隊的可觀測性能力？
- 工程師版：事故中，你能把使用者症狀、受影響服務、最近變更與相關依賴的訊號串起來嗎？
- L1：登入機器看 log
- L2：有 metrics 儀表板，但 logs 分散，出事要翻多處
- L3：符合服務需求的訊號（metrics、logs，以及有助診斷時的 traces）可互相關聯，核心服務有標準儀表板
- L4：能從使用者症狀往下鑽到根因，新服務上線預設帶標準可觀測性

**q10　告警設計**
- 主管版：告警設計的主要依據是什麼？
- 工程師版：手機響起時，通常是什麼樣的告警？
- L1：多為基礎設施層告警（CPU 高等），常被忽略
- L2：有分級，但噪音多，靠經驗判斷哪些可無視
- L3：以使用者影響／症狀為主，每條告警有 runbook
- L4：告警連結 SLO 燒耗率，並定期清理無效告警

**q11　🔎 告警有效率**
- 主管版：過去 30 天，需要人及時採取行動的 page 占比？每次送達值班者的 page 都計入（含重複）；以有效 page／全部 page 計算。無 page 或無紀錄請選無資料。
- 工程師版：過去 30 天，你的輪值收到的 page 有多少需要人及時採取行動？重複 page 也計入分母。無 page 或無紀錄請選無資料。
- 1：低於 25%
- 2：至少 25%，但低於 50%
- 3：至少 50%，但低於 80%
- 4：至少 80%，最高 100%
- 兩版皆提供額外選項：30 天內無 page，或紀錄不足

### 維度 4：變更與發布安全

**q12　發布流程**
- 主管版：發布流程的現況？
- 工程師版：你上次發布，從 merge 到上線的過程是什麼樣子？
- L1：手動部署，依個人經驗
- L2：有 CI/CD，但上線前人工檢查多，集中在少數時段
- L3：自動部署具備符合變更風險的檢查、受控發布，以及驗證過的回復途徑
- L4：發布風險依 SLO／錯誤預算動態調整，異常自動偵測並回滾

**q13　變更可追溯**
- 主管版：變更管理如何運作？
- 工程師版：出事時，你能多快知道「最近改了什麼」？
- L1：變更沒有紀錄
- L2：有變更單，但流於形式，與實際部署對不起來
- L3：變更可追溯，並可關聯到事故
- L4：變更失敗率有量測，並用來改進流程

**q14　🔎 變更事故回復時間**
- 主管版：六個月內最近一次變更事故，從發現到使用者可正常使用服務花了多久（不是到永久修復完成）？無事故請選無資料。
- 工程師版：六個月內最近一次變更事故，從發現到使用者可正常使用服務花了多久（不是到永久修復完成）？無事故紀錄請選無資料。
- 1：超過 240 分鐘
- 2：至少 60 分鐘，最多 240 分鐘
- 3：至少 15 分鐘，但低於 60 分鐘
- 4：低於 15 分鐘（含自動回滾）
- 兩版皆提供額外選項：六個月內無變更事故，或紀錄不足

### 維度 5：Toil 與自動化

**q15　Toil 認知與量測**
- 主管版：團隊如何看待與管理重複性維運工作？
- 工程師版：你一週有多少時間花在重複、手動、無長期價值的事？有人在算嗎？
- L1：沒人區分維運雜事與工程工作
- L2：大家都覺得很多，但沒有量化
- L3：用工單／值班紀錄量測 toil 占比，並有上限目標
- L4：保留固定工程時間消除 toil，並追蹤降幅

**q16　自動化現況**
- 主管版：自動化的現況？
- 工程師版：常做的維運操作，現在怎麼做？
- L1：個人腳本、口耳相傳
- L2：有腳本但散落各處，少人維護
- L3：重複性任務有共用且版本控管的自動化，IaC 為預設
- L4：自助化，服務擁有者不需開單即可完成常見操作

**q17　🔎 上一季消除了什麼**
- 主管版：上一季團隊消除了哪一件重複性工作？
- 工程師版：就你所知，上一季團隊消除了哪一件重複性工作？
- 1：沒有，或想不起來
- 2：有一兩件，但屬順手處理
- 3：有計畫地排進 sprint 並完成
- 4：有量化節省工時，並持續追蹤

### 維度 6：組織與治理

**q18　服務歸屬**
- 主管版：服務擁有權如何界定？
- 工程師版：半夜你的服務壞了，誰該被叫醒？大家有共識嗎？
- L1：沒人明確負責，出事找最熟的人
- L2：有服務清單，但 owner 常過期
- L3：每個核心服務有明確 owner 與 on-call 輪值，開發團隊共同承擔
- L4：服務有符合風險的上線準備檢查，並確認 owner、升級路徑與回復責任
- 工程師版提供額外選項：我不確定

**q19　值班健康度**
- 主管版：值班負擔如何被管理？
- 工程師版：你的值班體驗是什麼樣子？
- L1：少數人長期扛
- L2：有輪班，但常被夜間叫醒，疲勞明顯
- L3：輪值公平、有補休機制，夜間 page 有追蹤
- L4：追蹤值班中斷與疲勞，設有約定上限；超標會投入資源改善並追蹤效果

**q20　🔎 可靠性與交付衝突**
- 主管版：上一次可靠性與功能交付衝突，是怎麼決定的？
- 工程師版：你知道的最近一次可靠性與功能交付衝突，最後怎麼決定？
- 1：沒有機制，誰聲音大誰贏
- 2：主管臨時決定，可靠性通常讓步
- 3：有討論機制且依數據，但沒有約束力
- 4：有事先約定的政策（錯誤預算政策），且可靠性工作曾因此被優先排進
- 工程師版提供額外選項：我不確定

## 6. 建議引擎

建議的單位是**能力節點**，不是「補最弱維度」。

### 6.1 節點定義

`達成條件` 以題目答案等級判定（`0` 視為 1）。「前置」是節點之間的依賴，前置節點未達成時，該節點不推薦。

| 節點 | 名稱 | 前置 | 達成條件 |
|---|---|---|---|
| N1 | 基礎監控與服務清單 | 無 | q01 ≥ 2 且 q18 ≥ 2 |
| N2 | 定義核心服務 SLI | N1 | q01 ≥ 3 |
| N3 | 設定 SLO 與儀表板 | N2 | q02 ≥ 3 |
| N4 | 錯誤預算計算與定期檢視 | N3 | q03 ≥ 3 且 q04 ≥ 3 |
| N5 | 錯誤預算政策 | N4、N7 | q03 ≥ 4 且 q20 ≥ 4 |
| N6 | 事故分級與角色 | 無 | q05 ≥ 3 |
| N7 | 服務 owner 與 on-call 明確 | 無 | q18 ≥ 3 |
| N8 | 無究責 postmortem 與改善追蹤 | N6 | q06 ≥ 3 且 q08 ≥ 3 |
| N9 | 告警盤點與清理 | N1 | q10 ≥ 3 且 q11 ≥ 3 |
| N10 | SLO 燒耗率告警 | N3、N9 | q10 ≥ 4 |
| N11 | 漸進式發布與快速回滾 | 基本 CI/CD（q12 ≥ 2） | q12 ≥ 3 且 q14 ≥ 3 |
| N12 | Toil 量測與固定消除時間 | N7 | q15 ≥ 3 且 q17 ≥ 3 |
| N13 | 事故學習擴散 | N8 | q07 ≥ 3 |
| N14 | 可觀測性關聯（metrics、logs、traces） | N1 | q09 ≥ 3 |
| N15 | 變更可追溯 | 無 | q13 ≥ 3 |
| N16 | 共用自動化與 IaC | 無 | q16 ≥ 3 |
| N17 | 值班健康度管理 | N7 | q19 ≥ 3 |

**名詞：**

- **已達成：** 達成條件成立。
- **候選：** 未達成，且所有前置節點已達成。
- **受阻：** 未達成，且至少一個前置節點未達成。

### 6.2 排序規則（依序套用）

1. **過濾：** 受阻節點不推薦，改列入「暫緩」並說明缺哪個前置。例如 SLI 未建立，就不推薦錯誤預算政策。
2. **止血優先：** 若 q11 或 q19 的等級 ≤ 2（含「不確定」），且 N9 是候選，N9 排第一。人已經被告警壓垮時，談 SLO 沒有意義。
3. **基礎鏈優先：** 沿 N1 → N2 → N3 → N4 → N5 取第一個候選。
4. **其餘候選：** 依「觸發題最低分升冪」排序，同分取節點編號小者。
5. **數量限制，最多三條：**
   - **現在做：** 排序後第 1 名
   - **下一步：** 排序後第 2 名（沒有就不顯示）
   - **暫緩（含原因）：** 受阻節點中，觸發題最低分最小者；同分取「未達前置鏈最長」者（最遠的目標）；說明缺哪些前置
6. **規模調整：** `team = lt5` 時套用第 3.2 節規則。
7. **沒有候選也沒有受阻節點：** 顯示「目前沒有未達成的基礎節點」，並建議以 game day 或下次重測驗證。

### 6.3 行動措辭（依角色變化）

括號內的數字只是示例措辭，不是計算結果。

| 節點 | 主管版 | 工程師版：本週可做／可帶去跟主管說的一句話 |
|---|---|---|
| N1 | 一個月內建立核心服務清單（名稱、owner、依賴），確認每個服務至少有存活與錯誤率監控。 | 列出你負責的服務與監控現況。「我整理了服務清單，有三個服務目前沒有任何監控，想排時間補上。」 |
| N2 | 選一到兩個最影響使用者的服務，與產品一起定義成功率與延遲兩個 SLI，先量測、不訂目標。 | 從負載平衡器或 access log 算出一個服務的成功率與 p95 延遲。「我可以先用現有 log 算出成功率，不用新工具，要不要先看一個月的數字？」 |
| N3 | 以一個月的量測數據為基準訂出初版 SLO，放上共用儀表板，排每季檢視。 | 做一張只有 SLI 對 SLO 的單頁儀表板。「過去一個月成功率是 99.7%，文件寫的是 99.9%，要不要對一下？」 |
| N4 | 每月 review 固定五分鐘看剩餘錯誤預算，並記錄它是否影響了任何決策。 | 算出本月剩餘錯誤預算，貼進團隊週會。「這個月預算剩 20%，下週的大發布要不要先緩一下？」 |
| N5 | 與產品、工程主管共同簽署一頁政策：預算耗盡時凍結功能發布、優先做可靠性工作，並約定例外流程。 | 草擬一頁政策初稿帶去討論。「預算耗盡時我們沒有約定要做什麼，下次衝突還是誰聲音大誰贏，我先寫了一頁草案。」 |
| N6 | 定義三級嚴重度與事故指揮、對外溝通兩個固定角色，寫成一頁事故流程。 | 下次事故自願擔任記錄者，記下時間軸。「我們每次事故都臨時分工，能不能先定義誰是指揮？」 |
| N7 | 每個核心服務指定一位 owner 與一份輪值表，由開發團隊共同承擔。 | 檢查你的服務 owner 欄位是否過期，列出缺口。「這三個服務半夜壞了沒人確定該叫誰，我整理了清單。」 |
| N8 | 導入無究責格式，改善項目進正式 backlog（有負責人、期限），每月檢視結案率。 | 把上次事故的改善項目整理成工單。「上次事故的五個改善項目還沒人認領，我先建了工單。」 |
| N9 | 下一季指定一位 owner，盤點過去 30 天所有 page，砍掉或降級不需處理的告警，目標有效率超過 50%。 | 匯出自己上個月的 page 清單，標出哪些其實不用處理。「上個月 70% 的 page 不需處理，我想花兩天做告警盤點。」 |
| N10 | 核心服務改用多窗口燒耗率告警，取代單純閾值告警。 | 為一個服務做燒耗率告警，與舊告警並行一個月比較。「我想用一個服務試跑燒耗率告警，並行一個月，不影響現有告警。」 |
| N11 | 先挑一個服務導入 canary 或 blue-green，並演練一次回滾，以 15 分鐘內回復為目標。 | 把手動回滾步驟寫成腳本。「回滾現在要 40 分鐘，我可以先把步驟腳本化，目標壓到 15 分鐘。」 |
| N12 | 一個月內用工單或值班紀錄量測 toil 占比，並保留每個 sprint 固定比例的消除時間。 | 記錄一週所有重複性手動工作。「我這週有 30% 時間花在重複工作，前三名是這些，想排一項自動化。」 |
| N13 | 每月一次跨團隊事故分享，並統計重複原因。 | 把上次 postmortem 的一段重點發到共用頻道。「能不能每月留 30 分鐘，輪流分享一個事故？」 |
| N14 | 為核心服務建立標準儀表板與統一的請求 ID，使 metrics、logs、traces 可互相關聯。 | 在一個服務的 log 與 trace 加上共用 trace ID。「出事時我要開四個工具，加 trace ID 之後可以一步串起來。」 |
| N15 | 讓每次部署自動寫入變更紀錄，並可關聯到事故。 | 在儀表板疊加部署標記。「出事時我們不知道最近改了什麼，我可以先把部署事件疊到圖上。」 |
| N16 | 建立共用、版本控管的自動化庫，並規定基礎設施變更走 IaC。 | 把散落的腳本整理進共用 repo 並加 README。「我們有七支腳本在個人電腦上，想整理進一個 repo。」 |
| N17 | 追蹤夜間 page 數與輪值公平性，設定超標時觸發調整的規則。 | 記錄一個月的夜間 page 次數。「過去一個月我被夜間叫醒 9 次，想一起看怎麼降。」 |

## 8. 聯絡資料閘門（姓名＋Email）

### 8.1 位置與流程

```
首頁 → 角色與情境 → 20 題 → 【聯絡資料閘門】→ 結果頁
```

閘門放在**最後一題之後、結果頁之前**：此時使用者已投入時間，完成率影響最小，且動機最高（想看結果）。閘門畫面說明使用者即將得到：本次結果、可分享網址，以及後續可能寄送的進一步分析。

### 8.2 欄位

| 欄位 | 必填 | 驗證 |
|---|---|---|
| 姓名 | 是 | 1 到 100 字，去除前後空白 |
| Email | 是 | 格式驗證、轉小寫、最長 254 |
| 同意蒐集與聯絡 | **是**（勾選才能送出） | — |
| 同意接收相關內容與服務資訊 | 否（預設不勾） | — |
| 蜜罐欄位（隱藏） | — | 有值就靜默丟棄 |

**同意聲明參考文案**（上線前請由具專業的人確認；台灣個資法的告知義務與 GDPR（若有歐盟使用者）都需顧及）：

- 必填：「我同意 {營運者名稱} 蒐集我的姓名、Email 與本次填答內容，用於產生並寄送本次分析結果，以及後續與我聯絡。本同意僅適用於本問卷系統，詳見本系統的隱私權政策。」
- 選填：「我願意收到 SRE／DevOps 相關內容與服務資訊。」

### 8.3 資料流

1. 前端在瀏覽器內算好結果。
2. 使用者提交閘門表單 → 呼叫後端函式 `submit-assessment`（伺服器端再驗證一次）。
3. 函式寫入資料庫，前端導向結果頁。
4. **寫入失敗不阻擋結果顯示**：顯示不阻斷的提示並在背景重試，避免因後端問題讓使用者白填。
5. 使用者回到頁面：若答案完整且已提交，直接顯示結果；若未提交，回到閘門。

### 8.4 已知限制（v0.2 接受）

- **不做 Email 驗證。** 會有打錯與假 Email。日後「寄送結果」功能上線後，寄送本身即達成驗證。
- 閘門是 UI 層的軟閘門，結果在瀏覽器端計算，技術上可繞過。v0.2 可接受；若需強制，需把完整結果的產生移到伺服器端（v2 付費功能時處理）。

## 10. 多語系設計

### 10.1 目標

- 第一版：**zh-TW（來源語言）與 en**
- 預留：zh-CN、ja 與更多語系。**新增語系 ＝ 新增一個語系資料夾與一行設定，不改程式邏輯。**

### 10.2 原則

1. **邏輯與文字分離。** 計分、建議引擎、分享網址只使用語言中立的 ID（`q01`、`d1`、`N9`、選項級別 `1`–`4`），文字只存在於語系檔。
2. **畫面上零硬編碼文字。** 包含錯誤訊息、驗證訊息、按鈕、`aria-label`、圖表標籤、`<title>`。
3. **zh-TW 是來源語言。** 其他語系由來源翻譯而來；英文版翻譯需遵守術語表（第 10.4 節）。
4. **語系偵測順序：** URL `?lang=` → localStorage → 瀏覽器語言 → 預設 zh-TW。切換語系不得遺失已作答內容。
5. **退回鏈：** `zh-CN → zh-TW → en`；`ja → en`；其他 → `en`。缺 key 時依鏈退回，並在開發模式輸出警告。
6. 設定 `<html lang>`；日期、數字使用 `Intl`。
7. 提供鍵值一致性檢查（測試或腳本）：每個語系的 key 集合必須與 zh-TW 相同。

### 10.3 建議檔案結構

```
src/
  config/site.ts                 站名、營運者、聯絡信箱、部落格網址
  i18n/index.ts                  i18next 初始化
  i18n/languages.ts              語系清單（code、顯示名稱、htmlLang、是否啟用）
  locales/
    zh-TW/{common,questions,recommendations,legal}.json
    en/{common,questions,recommendations,legal}.json
    # 未來：zh-CN/、ja/ ...
  data/
    dimensions.ts                維度 ID、題目歸屬
    questions.ts                 題目 ID、類型、權重、各角色是否有 unsure 選項
    nodes.ts                     節點、前置、達成條件
    nodeArticles.ts              節點 → 部落格文章
  lib/
    scoring.ts                   純函式
    recommend.ts                 純函式
    shareUrl.ts                  編碼／解碼
supabase/functions/submit-assessment/
```

### 11.3 隱私頁（`/privacy`）

**本系統的隱私權政策是獨立文件，與部落格的隱私聲明完全分開，不可混為一談。**

須包含：

- 蒐集項目、目的、保存期間、利用對象與方式
- 使用者權利與刪除請求管道（本系統專用的聯絡信箱）
- localStorage 用途（作答進度、語系偏好、是否已提交）
- 受託處理者：資料由後端服務供應商（Lovable Cloud／Supabase）代為儲存，需如實列出
- 一段明確聲明：本系統與部落格是不同的網站，本政策只適用於本系統；本系統不與部落格交換任何資料

**實作限制：**

- 隱私頁不得引用、連結或沿用部落格的隱私聲明。
- 本系統不載入部落格的腳本、分析、Cookie 或任何嵌入元件。
- 建議文章連結（第 6.4 節）是外部連結，點擊後離開本系統，由部落格自己的政策管轄。
- 營運者名稱與聯絡信箱放在 `src/config/site.ts`，**沒有預設值**（不沿用部落格品牌），上線前務必填入真實值。
- 保存期間的預設值需要你決定（見第 14 節）。

### 11.4 瀏覽器端儲存

localStorage 只存：作答進度、語系偏好、是否已提交。**不存姓名與 Email。**

## 12. 技術架構

- **前端：** React、Vite、TypeScript、Tailwind、shadcn/ui、React Router
- **多語系：** react-i18next、i18next-browser-languagedetector
- **圖表：** Recharts 雷達圖。圖表旁提供等效資料表，供螢幕閱讀器與列印使用

- **路由：** `/`（首頁）、`/start`（角色與情境）、`/q/:n`（題目）、`/contact`（閘門）、`/results`（本人結果）、`/r`（分享檢視）、`/privacy`、404

**UX：**

- 一題一畫面，選定後自動前進，保留「上一題」；顯示進度條與預估剩餘時間
- 行動裝置優先；選項為大面積可點卡片；鍵盤可操作（數字鍵選項、Enter 前進）
- 符合 WCAG AA 對比；雷達圖有文字替代
- 結果頁提供列印樣式（可另存 PDF）
